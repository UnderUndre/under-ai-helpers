# SpecKit Review: 010-user-level-adaptation

**Reviewer**: trae
**Reviewed at**: 2026-06-25T14:02:00Z
**Commit**: 7fdaf53442ae8dcc1b5caa276b4f7d316014683a
**Artifacts reviewed**: spec.md, plan.md, tasks.md, data-model.md, contracts/ (index + 8 tool contracts), quickstart.md, research.md, constitution.md v1.5.0

## Summary

The spec-to-plan translation is strong: 18 FRs cleanly map to a focused extension of the underboard MCP server, the data model is internally coherent, and the sync/encryption design is appropriately scoped. However the feature ships with three real blockers — none caught by the author: (1) the entire agent-side adaptation depends on a skill that nothing ever tells agents to load, so US1 will silently no-op; (2) the inference engine has no documented signal-capture path — the schema stores signals but no task or contract describes how they get written; (3) the threat model for sync leaves a passphrase-handling gap that can leak the key. The pre-existing analyze.md (C1/H1/H2) is correct on the constitution and MCP-registration issues; this review confirms those and adds what the self-consistency pass could not see.

## Findings

| ID | Severity | Area | Finding | Recommendation |
|---|---|---|---|---|
| F1 | CRITICAL | Hidden assumption (G/H) | plan.md:104-109 + contracts/index.md:29-37 define the `.claude/skills/knowledge-adaptation/` skill that is the *sole* mechanism teaching agents to call `knowledge_profile_get` at session start and adapt depth. But no task and no `.claude/` wiring registers the skill in any agent's `skills:` frontmatter, CLAUDE.md, or a UserPromptSubmit/SessionStart hook. A skill file that no agent loads is inert markdown — US1 (P1, the entire value proposition) silently degrades to "agent never reads the profile, explains at default depth forever." This is the same class of defect as analyze's H1 (unregistered MCP tools) one layer up: registration at the transport (MCP) without registration at the consumer (agent skill loading). The skill's existence in `.claude/skills/` does NOT auto-load it — the repo's own mechanism (`.claude/hooks/agent-skills-reminder.sh`, per constitution §VIII) loads skills only when named in a spawned subagent's frontmatter. | Add a task: register `knowledge-adaptation` in the relevant agent frontmatter (at minimum `frontend-specialist`, `backend-specialist`, `debugger`, `orchestrator` — whichever the project expects to explain things) AND/OR a SessionStart/UserPromptSubmit hook that injects "load knowledge-adaptation skill" context. Without this, US1 cannot pass its acceptance scenario 1 ("Given level=beginner… explanation uses plain-language analogies"). |
| F2 | CRITICAL | Coverage gap / data flow (A/D) | data-model.md:58-74 defines `KnowledgeSignal` with `signal_type`, `signal_value`, `signal_metadata` and tasks T020 (inference-engine) + T021 (profile-signals tool) consume them. But **no task and no contract describes how signals are written**. The 9 MCP tool contracts cover get/set/config/signals/quiz/export/forget/sync — none is a "record-signal" tool. The inference engine (T020) reads signals to derive a level, but nothing in the system ever inserts a row into `knowledge_signals`. So inferred/hybrid modes (US3 acceptance scenarios 2 & 3, FR-008/FR-009) operate on an eternally-empty table — inference always returns "insufficient data, neutral default." The signal-capture path is the hidden backbone of half the feature and it is unspecified. | Decide and document the capture path: (a) an agent-side convention where the skill instructs agents to call a `knowledge_profile_record_signal` MCP tool after each interaction (add the tool + contract + task), OR (b) a hook (UserPromptSubmit/Stop) that extracts signals from the transcript and writes them, OR (c) piggyback on the existing dialog-capture infrastructure (spec 007). Whichever — add the task, the contract, and a test asserting signals actually accumulate. |
| F3 | HIGH | Security / privacy threat (E) | research.md:40-41 + data-model.md:22 specify `sync_passphrase_hash = PBKDF2 hash … for verification only — never stored in plaintext`, and tasks.md T026 says "PBKDF2 key derivation." But the contract (profile-sync.md) and data model do not specify (a) the PBKDF2 parameters (iterations, salt handling, salt storage), (b) whether the passphrase is requested per-sync-operation (good) or cached in the MCP server process memory (bad — long-lived MCP server, single user, but still a key-in-memory exposure), (c) what scrubs the derived key from memory after encryption/decryption. For a file whose stated threat model (research.md:16) is "the user's own cloud drive provider," a weak PBKDF2 iteration count (e.g. default 100k) is brute-forceable offline if the cloud file leaks. The spec FR-018 defaults signals to "most privacy-protective," but sync encryption has no equivalent floor. | Specify PBKDF2 parameters (recommend ≥600k iterations per OWASP 2023 guidance, random salt per-profile stored alongside the hash, salt NOT reused for the encryption key derivation). State explicitly: passphrase is NOT cached — requested per push/pull, key zeroed after use. Add a test asserting the iteration count and that the key buffer is overwritten. |
| F4 | HIGH | Missing edge case / failure mode (C/D) | profile-sync.md:36-57 (pull) + spec.md edge case "offline … retries on reconnect" (line 128). But nothing specifies what happens on a **partial write / interrupted sync file**. The sync file is AES-256-GCM encrypted JSON carried "via USB or a cloud drive" (research.md:40) — USB unplug mid-write, cloud-drive sync conflict producing a 0-byte or truncated file, or a partially-overwritten file from a crashed push. GCM authenticated decryption will reject a truncated ciphertext (good), but the pull contract returns only `TRANSPORT_FAILURE` with no recovery path: is the local profile left untouched (crash safety)? Is there an atomic-write guarantee on push (temp-file + rename)? Is a corrupted remote file distinguishable from "wrong passphrase"? An interrupted push that leaves a half-written encrypted file will make every subsequent pull fail with an opaque `TRANSPORT_FAILURE`, and the user has no documented recovery. | Specify: (a) push writes atomically (temp file + `fs.rename`), never leaving a partial encrypted file on disk; (b) pull validates GCM tag before touching local state — local profile is never mutated on a failed/decrypt-failed pull; (c) distinguish error codes: `CORRUPT_SYNC_FILE` (GCM tag fail / not valid JSON after decrypt) vs `WRONG_PASSPHRASE` (decryption fails) vs `TRANSPORT_UNAVAILABLE` (file not found / IO error). Add test cases for each. |
| F5 | HIGH | Hidden assumption / ambiguity (B/H) | spec.md FR-009 + data-model.md state transition diagram (line 123-128): "hybrid → engine PROPOSES update, user CONFIRMS." But there is no field, no tool, and no task for the user to **accept or reject** a proposal. `level_internal` is "current," `level_source` is "current source" — neither can represent "proposed-but-pending." analyze.md flagged this as M1 against the spec; I am escalating it to HIGH because it breaks US3 acceptance scenario 3 directly ("the assistant proposes a revision and waits for my confirmation rather than applying it") — that scenario is untestable as designed, and the implementer would have to invent the entire proposal lifecycle (schema migration + confirm tool + skill prompt wording + timeout/staleness for unconfirmed proposals) mid-implementation, which is exactly the kind of mid-flight rework the review gate exists to catch. | Add to data-model.md: `proposed_level_internal REAL NULL`, `proposed_at TEXT NULL`, `proposed_source TEXT NULL` on KnowledgeProfile. Add a confirm/reject path (either extend `profile_config` with `accept_proposed_revision`/`reject_proposed_revision`, or a dedicated `profile-revision` tool). Define proposal staleness (does an unconfirmed proposal from 30 days ago still bind?). Add a task for this and update T020. |
| F6 | MEDIUM | Logical consistency (A) | spec.md FR-016 ("expandable-hybrid … frontend, backend, database, ops") names concrete domains; data-model.md KnowledgeSubDomain leaves `domain_name` as free TEXT with no constraint. profile-config.md `expand_domain?: string` accepts any string. So a user can expand a domain `"Frontend"` and later query `"frontend"` and get two different rows / a silent miss. There is no canonical domain vocabulary, no case-folding rule, no reserved set. The skill (T010-T013) has no way to know which domain names to match conversation context against. | Define either a canonical domain vocabulary (frontend/backend/database/devops/security/docs — matching whatever the agent-routing table already uses) or an explicit case-fold + validation rule on `expand_domain`/`collapse_domain`/`domain` in get/set/config. Reject unknown domains with `UNKNOWN_DOMAIN` or warn. |
| F7 | MEDIUM | Missing edge case (C) | spec.md edge case line 127: "two teammates on the same project have very different levels — each receives explanations at their own level." But the data model keys profiles by `project_id` (stable_key = git remote URL), with **no user dimension**. A shared dev box, a paired-programming session, or a team that runs the same MCP server will see ONE profile for the project — whoever calibrates last wins. The "two teammates" edge case the spec explicitly calls out is actually unsolvable in this schema. | Either (a) acknowledge this is single-user-per-MCP-server by design and remove the misleading edge case from spec.md, OR (b) add a `user_id` dimension to the profile (OS username? MCP session id?) — which is a non-trivial scope change. Recommend (a) with a spec note: "multi-user per machine is out of scope; each user runs their own underboard instance." |
| F8 | MEDIUM | Performance / scale (F) | research.md:35 + tasks.md T020: inference runs "as a background tick, not in the request path." But nothing specifies what **triggers** the background tick. Options: (a) every N-th `profile_get` call, (b) a setInterval in the long-lived MCP server process, (c) on `profile_config`/`profile_set` writes. Each has tradeoffs: (a) starves if the user only ever reads via skill (never triggers re-eval), (b) means the MCP server holds a timer + writes to SQLite on a schedule (battery, background-process lifecycle), (c) misses inference when the user is read-only. Without a decision, T020's implementer picks one silently and the "N-signal cadence" (FR-009) is either never checked or checked at surprising times. | Specify the tick trigger in research.md or plan.md. Recommend (c)+lazy: evaluate on write-path (signal insert) and on-demand when `profile_get` is called and `signals_since_last_eval >= threshold`. Add to T020's description. |
| F9 | MEDIUM | Stakeholder clarity (H) | spec.md + contracts use "level" and "depth" sometimes interchangeably. FR-002 says "adapt explanation **depth**, vocabulary, and assumed prior knowledge." profile-get.md returns `level`. The skill teaches agents to adapt to a "level." But `level` is the user's *knowledge*, while `depth` is the *explanation's* property — they are inversely related in places (high user level → shallow explanation is appropriate for easy topics, deep for hard ones). A non-technical reader will conflate "set my level to expert" with "give me deep explanations always," which is wrong (an expert asking about a trivial topic should still get a short answer). | Disambiguate in spec.md glossary: `knowledge level` = user's assessed familiarity; `explanation depth` = how much the agent unpacks a given topic; the adaptation maps level → *default* depth but the agent still calibrates per-topic. One sentence in the skill (T013) suffices. |
| F10 | LOW | Constitution alignment (I) | plan.md:40 (Principle V justification): "Adding a skill `knowledge-adaptation` adds ~5 files to `.claude/skills/`. Justified: this skill is the essential agent-side bridge." The justification is correct *if* the skill is actually loaded (see F1). If F1 is not fixed, the skill fails Principle V's "earns its place by being invoked" test — it becomes a 5-file decoration that bloats every downstream session's context without effect. Conditional on F1. | Resolve F1 first; the Principle V justification then stands. If F1 is deferred, mark the skill experimental and exclude from the default transpile target until wired. |
| F11 | LOW | Alternative approaches (G) | research.md D006 considers "agent-level instruction" and rejects it as "too many agents to update." Reasonable, but a third option was not weighed: a **single line in CLAUDE.md** (the always-loaded instruction file) that says "At session start, call `knowledge_profile_get` and consult the knowledge-adaptation skill." CLAUDE.md is already in every session — one line there has stronger loading guarantees than a skill that depends on frontmatter registration. | Not blocking — but weigh whether a CLAUDE.md one-liner (cheap, universal) is safer than the skill-registration path (F1). Could do both. |

## Alternative approaches considered

- **Signal capture via existing 007 dialog-capture** (F2): the repo already has a dialog-capture hook (spec 007) that normalizes transcripts. Routing signal extraction through it (instead of a new record-signal tool) would reuse proven infrastructure and avoid a new MCP tool. Worth weighing against the bespoke-tool approach.
- **CLAUDE.md one-liner vs skill registration** (F11): see above. The always-loaded CLAUDE.md may be the lower-friction path to guaranteeing US1 actually works.
- **Multi-user profile dimension** (F7): adding `user_id` would make the "two teammates" edge case solvable, but it is a real scope increase (per-user calibration, per-user signals) and may not be worth it for a tool whose stated scale is "single-user, N projects." Recommend explicit out-of-scope rather than silent gap.
