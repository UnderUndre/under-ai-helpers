**Reviewer**: claude

## Summary

The fix pass after `trae.md` (commit 7fdaf53 → 9750c25) genuinely closed all of trae's prior blockers — skill registration (F1→FR-022/T033), signal capture (F2→FR-021/T022b), proposal lifecycle (F5→proposed_* fields), and the sync hardening surface (F3/F4→FR-023/T036) are now specified. This review audits the *fixed* artifacts and finds the fixes introduced a second layer of gaps the author didn't carry through to the schema. The headline weaknesses: (1) the lazy-tick cadence that replaced the old `setInterval` design has **no state in the schema to compute "signals since last eval" against** — the FR-009/FR-019 mechanism cannot be implemented as drawn; (2) the two flagship success criteria SC-001/SC-002 have **no wired measurement path** — the eval runner lives in the TS test harness but must score LLM-runtime skill output, and nothing bridges that gap; (3) the encrypted sync file is **not self-describing**, so a first-time pull on a second machine cannot derive the decryption key — US5's core promise is unimplementable as specified; (4) FR-024 ships **this repo's filled-in constitution** to every consumer, mis-governing their speckit pipeline. No CRITICALs (trae's two are truly resolved), but four HIGHs that each force mid-implementation rework.

## Alternative approaches considered

- **Eval bridge for SC-001/SC-002 (F2)**: rather than a bespoke LLM-call harness, the repo's existing 006 skill-eval machinery (cited in spec.md:16 as the model) may already have a record/replay pattern for scoring skill output. Reusing it would avoid inventing a second eval path — worth checking before building T030 fresh.
- **Signal-capture cadence state (F1)**: instead of a `last_inference_at` marker, an append-only `eval_runs` log (or a monotonic `signal_seq` high-water mark per profile) would make "since last eval" exact and also give the auditable-signals tool (FR-008) a natural evaluation history to expose. Heavier, but turns an implicit boundary into a queryable one.
- **Sync envelope (F3)**: the standard shape is a small JSON/binary header `{v, kdf:"pbkdf2", iters, salt, nonce}` + GCM ciphertext+tag. This is the conventional self-describing-file pattern; adopting it wholesale removes the first-pull bootstrap problem and future-proofs the iteration-count floor (the `sync_pbkdf2_iterations` migration note at data-model.md:26 already anticipates a rising floor — the file header is where that belongs, not the local DB).
