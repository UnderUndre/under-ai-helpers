## Summary

Impressively thorough spec-to-plan-to-tasks chain for a 7-user-story mega-feature. The pack pipeline design (US1) is clean: `.claude/` as source, pipeline-generated `packs/`, marketplace.json projection — respects Constitution Principles I/II rigorously. Guard hooks (US2) are the strongest design piece: fail-open/fail-closed split by severity, quote-stripping tokenizer, allowlist suffixes for `.env.example`. 

**Headline weaknesses**: (1) SC-005 ("conversion paths drop by half") is internally contradicted by research.md R6 which admits zero conversion transformers exist today — the metric is inflated. (2) The `presets apply` merge contract has no conflict-resolution semantics when allow and deny rules overlap for the same operation. (3) Four empirical verifications (V1–V4) are deferred to implementation but are architectural load-bearing — any one failing reshapes the design.

## Alternative approaches considered

1. **Guard hooks as a standalone npm package** instead of co-located in `.claude/hooks/`. Would allow versioning independent of packs and easier updates. Rejected because it adds a distribution dependency — the current pack-carried approach is simpler and the spec explicitly avoids new runtime deps.

2. **Event-sourced migration journal** for `helpers migrate` — instead of hash-comparing on every run, maintain a `.migrations` log of applied operations. Current design is stateless (pure function of tree state) which is cleaner for re-runnability, but makes it impossible to answer "what did migrate do last time?" without re-scanning. Low value add, not worth the complexity.

3. **Web-based marketplace catalog** served from GitHub Pages alongside the repo — would allow browsing packs without cloning. Nice-to-have, not required for any acceptance scenario, and adds a deployment concern. Log for potential follow-up.
